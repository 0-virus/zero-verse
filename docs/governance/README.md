# ZeroVerse 기획 심의 운영 규칙

중요한 제품·기술 결정과 범위가 큰 마일스톤을 기존 Claude 개발 ↔ Codex 계획·리뷰 파이프라인 안에서 검토하기 위한 규칙이다. 이 디렉터리는 Git으로 추적한다.

## 1. 팀 구성

회의는 다음 네 실행 주체로 고정한다.

| 주체 | 책임 |
|------|------|
| Codex 진행자 | 안건 정규화, 근거 문서 배포, 독립 에이전트 실행, 결과 종합, 위험 등급 판정, 회의록 작성 |
| Codex Product Reviewer | 사용자 가치, MVP 적합성, 범위와 성공 기준 검토 |
| Codex Architecture Reviewer | 기술 실현성, 아키텍처·데이터·API·보안·확장성 검토 |
| Codex Delivery & Risk Reviewer | 일정, 의존성, 테스트, 운영, 롤백과 전달 위험 검토 |

진행자와 세 검토자는 모두 Codex 에이전트다. Claude는 안건을 제기하거나 승인된 결과를 구현할 수 있지만 심의 구성원으로 참여하지 않는다.

세 검토 에이전트는 서로 독립된 컨텍스트에서 실행한다. 에이전트끼리 메시지, 중간 결과 또는 결론을 공유하지 않는다. 각 검토자는 자신의 권고안에 대한 가장 강한 반대 논거와 실패 시나리오를 반드시 제출한다.

Codex 진행자는 새로운 제품 요구사항을 만들거나 다수결로 결론을 정하지 않는다. 근거와 위험을 종합하고 이 문서의 승인 규칙을 적용한다.

## 2. 회의 소집 조건

다음 중 하나라도 해당하면 구현 전에 회의를 소집한다.

- `docs/PRD.md` 또는 `docs/REQUIREMENTS.md` 변경
- 인증, 권한, 개인정보 또는 보안 정책 변경
- DB 스키마 또는 공개 API 계약 변경
- 새로운 외부 라이브러리, 서비스 또는 인프라 도입
- `docs/design/` 정본과 기능 요구사항의 충돌
- 마일스톤 범위가 승인된 계획보다 20% 이상 증가
- 되돌리기 어렵거나 선행 마일스톤의 설계를 수정하는 결정
- PRD §9의 사용자 결정과 충돌
- 테스트 전략 또는 DoD를 충족하기 어렵다는 구체적 증거 발견

마일스톤 시작 시 아래 항목 중 두 개 이상에 해당하면 대형 마일스톤으로 보고 계획 직후 회의를 소집한다.

- 백엔드, 프론트엔드, 인프라 중 두 영역 이상 동시 변경
- 세 개 이상의 도메인에 영향
- 인증 또는 접근제어 포함
- DB 마이그레이션과 API 계약 변경을 함께 포함
- 외부 서비스 연동 포함
- 선행 마일스톤 설계 변경 필요
- 단일 PR로 검토하기 어려워 단계 분할 필요

구현 중 소집 조건이 발견되면 영향받는 작업만 보류한다. 독립적인 다른 작업은 계속할 수 있다.

## 3. 파이프라인

```text
Claude가 마일스톤 브랜치 생성
  -> Codex가 계획 작성
  -> Codex가 소집 조건 검사
     -> 미충족: Claude 개발
     -> 충족: 기획 심의
        -> 3개 독립 검토 병렬 실행
        -> Codex 진행자 종합 및 위험 등급 판정
        -> LOW: 자동 승인
        -> MEDIUM/HIGH/BLOCKED: 사용자 결정 대기
        -> 회의록, 결정 레지스터, 필요 시 ADR 갱신
  -> Claude가 승인된 결정만 구현
  -> Codex가 PR과 결정 문서의 일치 여부 리뷰
```

Codex 계획 단계와 Claude 개발 단계 모두 소집 조건을 검사할 책임이 있다. Claude가 개발 중 조건을 발견하면 임의 결정하지 않고 Codex 심의를 요청한다.

## 4. 회의 절차

1. Codex 진행자가 `meetings/MEETING-TEMPLATE.md`로 안건을 만든다.
2. 결정할 질문은 한 문장으로 제한하고 선택지, 제약, 제외 범위를 명시한다.
3. 진행자가 동일한 안건과 근거 목록을 세 독립 에이전트에 전달한다.
4. 각 에이전트는 `AGENT-BRIEFS.md`의 공통 출력 형식으로 한 번씩 검토한다.
5. Codex 진행자가 사실, 가정, 의견을 분리하고 합의점과 이견을 종합한다.
6. 승인 등급을 판정하고 회의록 상태를 갱신한다.
7. 승인된 결정이 구현에 지속적인 영향을 주면 ADR을 작성한다.
8. 해당 마일스톤 worklog의 `[이슈·결정]`에 회의록과 ADR 링크를 추가한다.

자유 토론이나 반복 설득 라운드는 기본적으로 열지 않는다. 근거가 부족하면 에이전트 간 토론 대신 `BLOCKED`로 분류하고 필요한 정보를 명시한다.

## 5. 승인 등급

| 등급 | 의미 | 처리 |
|------|------|------|
| `LOW` | 쉽게 되돌릴 수 있고 계약·DB·보안·범위에 영향 없음 | Codex 진행자가 자동 승인 |
| `MEDIUM` | 여러 모듈, 일정 또는 테스트 비용에 유의미한 영향 | 사용자 승인 필요 |
| `HIGH` | 요구사항, 보안, DB, 공개 API, 인프라 또는 PRD §9에 영향 | 사용자 승인 필요 |
| `BLOCKED` | 정본 충돌, 필수 정보 부족 또는 실현 가능성 판단 불가 | 사용자 결정 또는 정보 제공 전 보류 |

`LOW` 자동 승인은 다음 조건을 모두 만족할 때만 가능하다.

- 공개 API 변경 없음
- DB 스키마 변경 없음
- 인증·권한·개인정보 정책 변경 없음
- 새 외부 의존성 없음
- PRD, REQUIREMENTS, 디자인 정본 변경 없음
- 승인된 마일스톤 범위 증가 없음
- 현재 마일스톤 안에서 낮은 비용으로 롤백 가능
- 세 검토자 중 누구도 `HIGH` 또는 `BLOCKED` 근거를 제시하지 않음

하나라도 충족하지 못하면 최소 `MEDIUM`으로 올린다. 확신도가 낮다는 이유로 `LOW`를 부여하지 않는다.

## 6. 문서 규칙

| 문서 | 위치 | 목적 |
|------|------|------|
| 회의록 | `meetings/M{n}-YYYYMMDD-<slug>.md` | 검토 과정, 근거, 이견, 승인 상태 |
| ADR | `decisions/ADR-NNNN-<slug>.md` | 지속적인 기술·제품 결정 |
| 결정 레지스터 | `DECISION-REGISTER.md` | 결정과 상태의 단일 인덱스 |
| 위험 레지스터 | `RISK-REGISTER.md` | 마일스톤을 넘는 미해결 위험 |
| 개발 로그 | `../worklog/M{n}-<slug>.md` | 회의록·ADR 링크와 구현 경과 |

마일스톤에 속하지 않는 안건은 회의록 접두사로 `X`를 사용한다. 승인된 회의록의 기존 결론은 덮어쓰지 않는다. 변경은 `정정 기록`에 append하거나 새 회의를 열어 이전 문서를 대체한다.

PRD §9에는 사용자 확정 사항이나 정본 충돌을 해결한 결정만 반영한다. 일반적인 기술 선택은 ADR에만 기록한다.

회의 상태는 다음 값만 사용한다.

```text
PROPOSED
REVIEWING
AUTO_APPROVED
USER_DECISION_REQUIRED
APPROVED
REJECTED
BLOCKED
SUPERSEDED
```

## 7. 근거 우선순위

검토자는 루트 `AGENTS.md`의 소스 오브 트루스 우선순위를 그대로 따른다.

1. 사용자의 명시적 결정과 PRD §9
2. `docs/design/`의 시각 디자인 정본
3. `docs/REQUIREMENTS.md`의 데이터·API·비즈니스 규칙
4. `docs/PRD.md` 본문
5. 현재 마일스톤 worklog와 기존 ADR

모든 핵심 주장은 파일 경로와 섹션, FR/NFR 또는 ADR을 근거로 표시한다. 근거가 없는 내용은 사실이 아니라 가정으로 기록한다.
