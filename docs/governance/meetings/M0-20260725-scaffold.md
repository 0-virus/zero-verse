# Planning Review: M0 프로젝트 스캐폴딩 계획

- 회의 ID: `M0-20260725-scaffold`
- 관련 마일스톤: `M0`
- 상태: `APPROVED`
- 소집 사유: 전체 MVP DB 스키마와 공통 공개 API 계약을 처음 도입하고, 백엔드·프론트엔드·DB 테스트 인프라를 동시에 변경하는 대형 마일스톤이므로 구현 전 심의가 필요하다.
- 생성 일시: 2026-07-25
- 진행자: Codex
- 관련 worklog: `../../worklog/M0-scaffold.md`
- 관련 ADR: [`ADR-0002`](../decisions/ADR-0002-non-domain-error-taxonomy.md) (ACCEPTED, 2026-07-25)

## 1. 결정할 질문

공통 예외 처리의 비도메인 오류인 Bean Validation·미매핑 경로·처리되지 않은 500을 **(A)** `VALIDATION_*`·`COMMON_*` prefix로 분류하고 `docs/REQUIREMENTS.md` NFR-04를 개정할 것인가, **(B)** 요청 도메인의 기존 prefix로 매핑할 것인가, **(C)** M0에서는 `BusinessException` 계열만 확정하고 나머지는 후속 마일스톤으로 보류할 것인가?

## 2. 배경과 범위

### 배경

M0는 이후 모든 마일스톤의 선행 작업으로서 Spring Boot·Flyway·공통 응답 및 예외 처리·프론트엔드 라우터와 디자인 기반을 구축한다.

`docs/REQUIREMENTS.md` NFR-03은 Bean Validation 400, 리소스 없음 404, 인증·권한 및 중복 오류의 HTTP 상태 구분을 요구한다. 그러나 NFR-04에는 비즈니스 도메인 prefix만 존재하며 Bean Validation·미매핑 경로·처리되지 않은 500에 대응하는 공통 코드가 없다.

동시에 M0는 도메인 Java 엔티티를 만들지 않으면서 첫 Flyway 마이그레이션에서 MVP 전체 12개 테이블을 생성하고, Testcontainers MySQL 8.4로 이를 검증하는 계획이다. 현재 Docker client는 있으나 daemon의 Server 응답이 없어 필수 DB 통합 테스트를 실행할 수 없는 상태로 보고되었다.

### 포함 범위

- 비도메인 오류의 공개 에러 코드 분류 방식 A/B/C
- `V1__init.sql`에서 전체 12개 테이블을 먼저 생성하는 스키마 우선 방식의 타당성
- 초기화 이전 백엔드·SQL·테스트 자산의 파일별 선별 이식
- 현재 디자인 정본에 따른 프론트엔드 재작성
- Testcontainers MySQL 8.4를 M0 DB 테스트 정본으로 사용하는 방식
- M0에 적용되는 PRD §11 테스트와 §12 DoD의 경계
- M0 구현·검토 단위와 공용 UI 범위

### 제외 범위

- M1 이후 도메인 기능별 오류 코드
- JWT 401·403 정책과 인증 실패 응답
- 이미지 업로드 및 S3 오류
- 도메인 Java 엔티티·Repository·Service·Controller 구현
- M1 이후 기능 화면의 실제 API 연동과 완전한 시각 검증

### 제약

- 공통 응답의 `success/data/error/timestamp` 구조를 유지한다.
- HTTP 400·404·500 구분을 유지한다.
- 비즈니스 오류에 적용되는 기존 도메인 prefix 규칙을 유지한다.
- 정본에 없는 에러 코드를 구현 전에 임의로 만들지 않는다.
- NFR-04 개정과 공개 API 계약 변경에는 사용자 승인이 필요하다.
- 첫 Flyway 마이그레이션은 MVP 전체 도메인 테이블을 생성해야 한다.
- 테스트 정본은 MySQL 8.x이며 계획상 수용 버전은 Testcontainers `mysql:8.4`이다.
- M0 테스트에 placeholder·`skip`·stub·조건부 성공을 허용하지 않는다.
- 프론트엔드는 현재 `docs/design/` 정본을 따르며 폐기된 다크 네온 디자인을 재사용하지 않는다.

## 6. Codex 진행자 종합

### 합의점

- 세 검토자 모두 선택지 A를 권고했다.
- 세 검토자 모두 `APPROVE_WITH_CHANGES`, 확신도 92 이상, 제안 위험 등급 `HIGH`를 제출했다.
- A는 비도메인 오류를 임의의 비즈니스 도메인에 귀속시키지 않는다는 점에서 B보다 의미적으로 일관된다.
- C는 더 가역적일 수 있으나, 선택하면 M0의 GlobalExceptionHandler·Bean Validation 계약과 완료 판정도 함께 보류해야 한다.
- A는 NFR-04와 공개 API 계약을 변경하므로 구현 전에 사용자 승인이 필요하다.
- 도메인 Java 엔티티 없이 전체 12개 테이블을 V1에서 먼저 생성하는 방식은 현재 정본과 일치한다.
- 이 비대칭에서는 `ddl-auto=validate`만으로 충분하지 않으며 실제 MySQL 8.4에서 metadata·INSERT·제약 위반을 검증해야 한다.
- 초기화 이전 자산은 커밋 전체를 재사용하지 않고 파일별로 현재 정본과 대조해 선별 이식해야 한다.
- 이전 프론트엔드 코드는 폐기된 디자인을 포함하므로 현재 디자인 정본에 맞춰 재작성해야 한다.
- Docker daemon의 Server 응답과 Testcontainers `mysql:8.4` 전체 테스트 통과는 M0 완료의 필수 게이트다.
- M0에는 PRD §11·§12 중 현재 구현 범위에 해당하는 테스트만 적용하되, 그 테스트에는 placeholder·`skip`·stub을 허용하지 않는다.
- 공용 UI와 화면은 M0 골격 범위로 제한하고 완성된 도메인 화면이나 실제 API 연동으로 간주하지 않아야 한다.

### 이견

- Delivery & Risk Reviewer는 M0를 최소 3개의 독립 PR 또는 이에 준하는 검토 단위로 분할해야 한다고 보았다. Product와 Architecture Reviewer도 범위 축소와 독립 검증 필요성에는 동의했지만, 반드시 3개의 별도 PR이어야 한다고 명시하지는 않았다.
- 공용 UI 14종을 유지할지 실제 M0 소비 범위로 축소할지에 대한 구체적인 목록은 합의되지 않았다. 다만 TODO·빈 구현과 소비처 없는 도메인 API의 조기 확정은 허용하지 않는다는 점에는 합의가 있다.
- `VALIDATION_*`·`COMMON_*`의 정확한 식별자는 아직 사용자 확정 사항이 아니다. Architecture Reviewer는 `VALIDATION_001`, `COMMON_404`, `COMMON_500`을 예시로 제시했지만 정본에 아직 존재하지 않는다.
- Docker 미가용은 계획 승인 자체를 막는 `BLOCKED` 사유인지에 관해 강한 반대 논거가 제출되었다. 다만 세 검토자의 최종 권고는 모두 계획을 `BLOCKED`로 판정하지 않고, 완료 전 하드 게이트로 처리하는 것이었다.

### 확인된 사실

- NFR-04에는 `AUTH/USER/BLOG/POST/CAT/UNI/COM/LIKE/NOT/ADMIN/UPLOAD` prefix만 있으며 공통·검증 prefix는 없다.
- PRD §4.4와 §10 M0는 `GlobalExceptionHandler`, `ErrorCode`, Bean Validation 400 처리를 M0 범위로 둔다.
- NFR-07은 첫 Flyway 마이그레이션에서 MVP 전체 도메인 테이블을 생성하도록 요구한다.
- PRD §10 M0의 Java 범위는 공통 기반이며 도메인 엔티티·기능은 M1 이후에 배치되어 있다.
- 이전 V1과 관련 테스트는 MySQL 8.4에서 generated-column 관련 오류를 검출한 이력이 있다.
- 이전 프론트엔드는 현재 폐기된 디자인 정본을 사용했다.
- 제출된 환경 점검 결과 Docker daemon의 Server 응답이 없으며 현재 Testcontainers 테스트를 실행할 수 없다.
- PRD §11·§12는 마일스톤마다 해당 범위의 실제 테스트 통과를 요구한다.

### 미확인 가정

- V1이 공유·운영 환경 또는 보존해야 할 데이터가 있는 환경에 아직 적용되지 않았다.
- M0 완료 전에 Docker daemon 접근과 `mysql:8.4` 이미지 실행 권한·네트워크가 확보된다.
- Auditing 테스트용 엔티티와 테이블을 운영 V1에서 완전히 격리할 수 있다.
- 외부 API 소비자가 아직 없어 공통 에러 계약을 현재 낮은 비용으로 조정할 수 있다.
- 15개 라우트의 빈 상태가 후속 기능을 흉내 내는 stub이 아니라 완결된 라우팅·레이아웃 스캐폴딩으로 제한된다.

### 권고안

진행자는 **선택지 A를 권고**한다.

Bean Validation은 `VALIDATION_*`, 미매핑 경로와 처리되지 않은 500은 `COMMON_*` 책임으로 분리하는 것이 원인과 코드 의미를 일치시킨다. B는 요청 도메인이 없는 오류를 설명할 수 없고, C는 M0 글로벌 예외 처리 계약과 테스트를 완결하지 못한다.

다만 다음 사항은 권고이지 확정 결정이 아니다.

- A 채택 및 NFR-04 개정은 공개 API·요구사항 정본 변경이므로 사용자가 승인해야 한다.
- 최소 코드 후보는 `VALIDATION_001`, `COMMON_404`, `COMMON_500`으로 제한하는 방안을 권고한다.
- `COMMON_500`은 고정된 외부 메시지를 사용하고 stack trace·SQL·내부 예외 메시지를 응답에 포함하지 않아야 한다.
- M0 계획은 아래 필수 변경을 반영하는 조건으로만 승인하는 것이 타당하다.
- Docker 미가용은 계획 심의를 `BLOCKED`로 만들지는 않지만, Docker Server 응답과 전체 MySQL 8.4 테스트 green 없이는 M0를 완료·머지할 수 없다.

### 위험 등급

- 등급: `HIGH`
- 판정 근거:
  - A는 NFR-04와 공개 API 에러 계약을 변경한다.
  - M0는 전체 MVP DB 스키마를 최초 도입한다.
  - Spring Boot·Flyway·QueryDSL·SpringDoc·Testcontainers·React·Tailwind 등 새 외부 의존성과 인프라를 도입한다.
  - 백엔드·프론트엔드·DB 테스트 기반을 함께 변경하며 여러 후속 마일스톤에 지속적인 영향을 준다.
  - 세 검토자 모두 구체적인 `HIGH` 근거를 제시했다.
- 자동 승인 조건 충족 여부: 불충족

| LOW 자동 승인 조건 | 판정 | 근거 |
