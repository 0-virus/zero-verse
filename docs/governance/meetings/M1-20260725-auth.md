- 회의 ID: `M1-20260725-auth`
- 관련 마일스톤: `M1`
- 상태: `APPROVED`
- 소집 사유: 인증·권한·보안 정책 변경, 공개 API 오류 계약 변경, 신규 외부 라이브러리 JJWT 도입, 백엔드·프론트엔드 및 4개 도메인 동시 변경, M0 보안 설정 교체

## 1. 결정할 질문

M1을 **A안**(JJWT 0.13.0·HS256, row-lock Refresh Token rotation, `SameSite=Strict` 쿠키, register 후 프론트엔드 자동 signin을 채택하고 `docs/REQUIREMENTS.md` NFR-04에 이메일 중복 및 일반 Access 인증 실패 코드를 추가), **B안**(새 오류 코드 없이 기존 `AUTH_001~003` 및 `USER_*` 코드를 재사용), 또는 **C안**(필수 계약과 운영 배치 정보가 확정될 때까지 영향받는 M1 인증 구현을 보류) 중 어느 방식으로 진행할 것인가?

## 2. 배경과 범위

### 배경

M1은 FR-AUTH-01~05를 구현하며 User·Blog·Category·RefreshToken, JWT 인증, Refresh Token rotation, 쿠키, 보안 필터, 프론트엔드 인증 상태와 로그인·회원가입 화면을 함께 다룬다.

현 정본에서 `AUTH_001`은 로그인 실패, `AUTH_002`는 Access Token 만료, `AUTH_003`은 Refresh Token 무효로 의미가 고정되어 있다. 반면 이메일 중복 409와 만료 외 일반 Access 인증 실패를 정확하게 나타낼 전용 오류 코드가 없다.

따라서 A안은 오류 의미를 보존하지만 `docs/REQUIREMENTS.md` NFR-04와 공개 API 계약을 변경한다. B안은 문서 변경을 피하지만 기존 오류 코드 의미를 확대하거나 왜곡해야 한다.

### 포함 범위

- JJWT 0.13.0 및 HS256 기반 Access·Refresh JWT
- Access Token 1시간, Refresh Token 2주
- Refresh JWT의 SHA-256 해시 저장 및 `jti` 조회
- 비관적 row lock을 이용한 Refresh Token rotation
- `SameSite=Strict`, HttpOnly, 제한된 path, 운영 `Secure=true` 쿠키
- User·기본 Blog·DEFAULT “미분류” Category의 가입 트랜잭션
- nickname 기반 slug 및 `blog`, `blog-2` 형식의 fallback
- M0 `anyRequest().permitAll()` 제거와 401·403 회귀 검증
- AuthContext, apiClient, 라우팅 가드, 로그인·회원가입 화면
- 초기화 이전 M1 자산에서 의도와 회귀 테스트 사례만 선별 이식

### 제외 범위

- OAuth·소셜 로그인
- 이메일 인증
- 기기별 세션 관리
- 폐기된 Refresh Token 재사용 감지 시 사용자 전체 세션 폐기
- `/users/me`
- 블로그 초기설정 API
- 카테고리 CRUD
- M2 이후 도메인 기능
- V1 migration 수정

### 제약

- `AUTH_001`은 signin 실패, `AUTH_002`는 만료된 Access Token, `AUTH_003`은 Refresh Token 무효라는 기존 의미를 유지한다.
- `V1__init.sql`은 변경하지 않는다. 스키마 변경 필요 시 V2 이상 forward migration과 별도 재심의가 필요하다.
- `User.name`은 필수이고 `birth_date`는 nullable이다.
- M0의 `anyRequest().permitAll()` 제거 및 대표 보호 API의 401·403 검증은 RISK-0002 종료 게이트다.
- Access Token은 프론트엔드 메모리에만 저장한다.
- Refresh Token은 HttpOnly Secure SameSite 쿠키로 전달하며 rotation이 필수다.
- 새로운 제품 요구사항은 본 심의에서 만들지 않는다.
- 운영 프론트엔드와 API가 cross-site라면 `SameSite=Strict` 정책을 그대로 확정하지 않고 별도 재심의한다.

## 6. Codex 진행자 종합

### 합의점

- 세 검토자 모두 A안을 1차 권고했다.
- 세 검토자 모두 `APPROVE_WITH_CHANGES`, 확신도 92~93, 위험 등급 `HIGH`를 제안했다.
- B안은 기존 `AUTH_001~003`의 의미를 훼손하거나 이메일 중복 409를 부정확하게 표현하므로 권고되지 않는다.
- A안은 `docs/REQUIREMENTS.md` NFR-04와 공개 API 계약을 변경하므로 사용자 승인이 필요하다.
- Access 1시간, Refresh 2주, raw Refresh JWT 해시 저장, `jti` 조회 및 row-lock rotation은 정본과 양립한다.
- User·Blog·DEFAULT Category의 가입 트랜잭션과 RefreshToken을 포함한 네 엔티티는 M1 인증 흐름에 필요하다.
- M0의 `anyRequest().permitAll()`은 제거해야 하며 401·403 응답 본문까지 검증해야 한다.
- 운영 FE/API의 site 관계와 실제 브라우저 쿠키 검증이 필요하다.
- slug 동시 충돌은 사전 조회만으로 충분하지 않으며 DB unique를 최종 권위로 삼아야 한다.
- register 성공 뒤 자동 signin만 실패한 상태를 가입 실패와 구분해야 한다.
- 초기화 이전 소스의 전체 복사나 체리픽은 부적절하며 의도와 회귀 테스트 사례만 선별 이식하는 것이 타당하다.

### 이견

실질적인 A/B 결론에는 이견이 없다. 세부 강조점에는 다음 차이가 있다.

- Product Reviewer는 자동 signin 부분 실패의 사용자 복구 경험과 가입 완료 상태 보존을 가장 강조했다.
- Architecture Reviewer는 slug 원자성, signout/refresh 경합, Origin 기반 CSRF 완화와 method 단위 matcher를 가장 강조했다.
- Delivery & Risk Reviewer는 실제 브라우저 검증, 단계별 리뷰·배포·롤백 및 구조화 보안 로그를 가장 강조했다.
- 운영 배치 정보가 없는 상황을 `BLOCKED`로 볼 수 있다는 반론이 제시됐으나, 세 검토자 모두 필요한 조건을 특정할 수 있고 A안의 실현 가능성을 판단했으므로 현재 판정은 `BLOCKED`가 아니라 사용자 승인이 필요한 `HIGH`다. 단, cross-site 배치라면 쿠키 정책 부분을 다시 심의해야 한다.

### 확인된 사실

- `AUTH_001`, `AUTH_002`, `AUTH_003`의 기존 의미는 각각 signin 실패, Access Token 만료, Refresh Token 무효로 정본에 고정되어 있다.
- 이메일 중복 409와 만료 외 일반 Access 인증 실패를 정확하게 표현할 전용 코드가 현재 정본에 없다.
- A안은 REQUIREMENTS 및 공개 API 오류 계약 변경이다.
- M1은 신규 외부 의존성 JJWT를 도입한다.
- 인증·보안 정책과 M0 SecurityConfig가 변경된다.
- V1에는 Refresh Token의 `token_id`, hash, 만료·폐기 및 갱신 시각을 저장할 구조가 있으며 V1 변경은 계획되지 않았다.
- `anyRequest().permitAll()` 잔존은 RISK-0002로 이미 등록되어 있다.
- 가입 시 User·기본 Blog·DEFAULT Category를 생성하는 것은 기존 요구사항이다.
- 전체 세션 폐기는 본 안건의 명시적 제외 범위다.

### 미확인 가정

- 운영 FE와 API가 동일 schemeful site로 배치된다.
- 운영 HTTPS 종료 이후에도 Secure Refresh 쿠키가 정상 전달된다.
- cross-site 배치가 필요하지 않다.
- 실제 운영 MySQL이 테스트 환경과 같은 비관적 잠금 동작을 제공한다.
- JWT secret이 최소 256-bit 엔트로피로 안전하게 주입되고 누락 시 애플리케이션이 시작되지 않는다.
- 자동 signin 실패 시 이미 생성된 계정을 유지하고 일반 signin으로 복구시키는 UX를 사용자가 승인한다.
- fallback slug가 M2 초기설정 전에 영구 URL로 잘못 안내되지 않는다.
- BE와 FE를 순차 리뷰·배포 단위로 나눌 수 있다.

### 권고안

**1차 결정 질문에 대한 진행자 종합 권고는 A안이다. 단, 아래 필수 변경과 사용자 결정을 구현 전에 완료하는 조건부 권고다.**

근거:

1. B안은 기존 오류 코드의 고정된 의미와 이메일 중복 409 규칙을 동시에 만족할 수 없다.
2. A안은 로그인 실패, Access 인증 실패, Refresh 실패, 이메일 중복을 분리해 FE 복구 동작과 운영 관측을 명확하게 만든다.
3. row-lock rotation, 가입 트랜잭션 및 네 엔티티 범위는 기존 스키마와 M1 요구사항 안에서 구현 가능하다.
4. 확인된 위험은 method 제한, DB 기반 동시성 테스트, Origin/CSRF 방어, 실제 브라우저 검증 및 부분 실패 UX로 완화할 수 있다.

6. 세 검토자의 일치 자체가 결정 근거는 아니다. 정본 의미 보존, 구현 가능성 및 위험 완화 가능성이 A안 권고의 근거다.

### 2026-07-26 · 필수 변경 #12(브라우저 E2E) 이관 — 사용자 승인

**원 요구**: "로컬 `localhost:5173`→백엔드와 운영 유사 HTTPS 환경에서 signin→cookie 저장→
refresh rotation→signout을 실제 브라우저로 검증하는 smoke/E2E 테스트를 DoD에 추가한다."

**변경**: M1 완료 조건에서 제외하고 **최초 배포 전 필수**로 이관한다.

- **사유**: 로컬에 HTTPS 종단이 없고 운영 배포 환경도 아직 없다. `Secure=true`·
  `SameSite=Strict` 쿠키는 http에서 저장되지 않아 로컬 http로는 계약을 재현할 수 없다.
  환경이 갖춰지기 전에는 수행 자체가 불가능하다.
- **승인**: 사용자 결정 2026-07-26. Codex 재리뷰가 "수행하거나 명시적 연기 승인 전까지
  머지 차단"으로 판정한 데 대한 응답이다.
- **대체 검증**(M1에서 실제로 수행): MockMvc로 Set-Cookie 전체 계약(HttpOnly·SameSite=Strict·
  Path·Max-Age=1209600, 삭제 쿠키 Max-Age=0), rotation 단일 성공·재사용 거부·signout
  idempotent, Origin/Referer fail-closed. FE는 jsdom으로 apiClient single-flight·지연 401
  경쟁·StrictMode 이중 실행·세션 복구.
- **남은 위험**: 브라우저의 실제 쿠키 저장·전송 동작은 미검증이다. **`RISK-0005`에 이 항목을
  배포 전 게이트로 편입**한다.
- **재검토 조건**: 운영 배포 환경이 확정되거나 로컬 HTTPS 종단이 마련되는 시점.
