1. FR-SETTINGS-02의 현재 비밀번호 불일치를 `USER_005` + 400으로, FR-SETTINGS-04의 완료된 초기설정 재호출을 `BLOG_004` + 409로 신설하고 기존 `AUTH_001~004`·`USER_004` 의미를 보존할 것인가(A), 기존 코드를 재사용할 것인가(B), 계약 확정을 보류할 것인가(C)?
2. FR-SETTINGS-03의 `url_slug` 수정 허용을 API 정책으로 유지하고 `/blog/setup`의 “나중에 변경할 수 없어요” 카피를 변경 가능 안내로 개정할 것인가(A), 디자인 카피에 맞춰 API를 초기설정 후 불변으로 바꿀 것인가(B), 모순된 카피와 API를 그대로 둘 것인가(C)?

## 2. 배경과 범위

### 배경

M2는 FR-SETTINGS-01~04와 FR-BLOG-01을 구현한다. commit `6e6cf63`의 계획은 현재 비밀번호 불일치와 초기설정 재호출에 대응할 전용 오류 코드가 NFR-04에 없고, 디자인의 slug 불변 카피가 `PUT /blogs/me`의 slug 수정 계약과 충돌하며, 실제 브라우저 E2E runner가 설치되지 않은 상태임을 확인했다.

회의는 `docs/governance/README.md` §2의 다음 소집 조건을 충족한다.

- 신규 설정·공개 조회 API와 오류 코드는 공개 API 계약에 영향을 준다.
- 현재 비밀번호 확인, 프로필 개인정보와 principal 기반 자기 정보 접근은 인증·권한·개인정보 정책에 해당한다.
- `docs/design/`의 slug 불변 카피와 REQUIREMENTS FR-SETTINGS-03·04가 충돌한다.
- Playwright/Cypress 채택 시 새 외부 의존성이 추가된다.
- BE·FE 동시 변경과 인증/접근제어 포함으로 대형 마일스톤 조건 두 개를 충족한다.

### 포함 범위

- `GET/PUT /api/v1/users/me`, `PUT /api/v1/users/me/password`
- `GET/PUT /api/v1/blogs/me`, `PUT /api/v1/blogs/me/initial-setup`
- `GET /api/v1/blogs/slug/{urlSlug}`
- BlogInitialSetupPage, SettingsProfilePage, BlogPage의 실제 API 연동
- 오류 코드·HTTP 상태·FE 복구 분기·Swagger·테스트 계약
- slug 수정 정책과 `/blog/setup` 안내 카피
- M2 자동 테스트 범위, 1440px 시각 대조, 최초 배포 전 브라우저 게이트

### 제외 범위

- FR-BLOG-02 게시글 목록, 카테고리 CRUD, 게시글, 업로드, 회원 탈퇴, 유니버스·댓글·피드·알림·관리자
- slug 이력·alias·기존 URL redirect 기능
- 별도 slug availability API
- V1 수정 또는 신규 DB migration
- 최초 배포 환경 자체의 구축

### 제약

- 기존 `AUTH_001~004`·`USER_004` 의미를 변경하지 않는다. (`ADR-0003`, PRD §9.4-AB)
- 성공·실패 공통 응답, HTTP 상태, 도메인 prefix 규칙을 지킨다. (REQUIREMENTS NFR-03·04, PRD §4.1·§4.4)
- slug 형식·예약어·unique와 nickname 변경 시 slug 비연동을 유지한다. (REQUIREMENTS §5, FR-SETTINGS-01·03)
- 저장·수정 허용 정책은 REQUIREMENTS, 시각·카피는 디자인 정본이 담당한다. 새 충돌은 사용자 결정 없이 임의 해결하지 않는다. (루트 `AGENTS.md`, PRD §0·§9.0, governance §7)
- M2 범위를 늘리지 않고 NFR-09와 PRD §11~§12의 실행 가능한 테스트·DoD를 충족한다.
- 사용자 승인 전 오류 코드 의미, slug 정책 override 또는 새 runner를 구현에 고정하지 않는다.

세 리뷰어는 동일한 의제·선택지·제약·근거 목록과 진행자의 초기 추론을 서로 독립된 컨텍스트에서 받았다. 리뷰어 간 메시지, 중간 결과 또는 결론은 공유하지 않았다.

### Product Reviewer

- 권고: `APPROVE_WITH_CHANGES`
- 확신도: 94
- 제안 위험 등급: `HIGH`

#### 근거가 확인된 사실

- **Q1=A.** 현재 비밀번호 불일치는 인증 완료 사용자의 설정 검증이고, initial-setup 재호출은 Blog 상태 충돌이다. 전용 코드는 FE의 “비밀번호 재입력”과 “setup 이탈” 복구를 분리하면서 ADR-0003의 기존 의미 보존 원칙을 따른다. (FR-SETTINGS-02·04, NFR-03·04, PRD §4.4·§5.2·§9.4-AB, ADR-0003)
- **Q2=A.** slug 수정 가능성은 데이터·API 정책 정본에 명시되어 있다. 불변 카피를 유지하면 사용자에게 영구 주소라고 약속하면서 Settings에서 변경을 허용하는 모순이 생긴다. 정책은 유지하고 사용자 승인으로 카피를 정합화해야 한다. (REQUIREMENTS §5, FR-SETTINGS-03·04, PRD §7·§9.0, DESIGN-SYSTEM §8.6, governance §7)
- **Q3=B.** M2 자동 통합·라우팅·시각 검증은 유지하되 운영 Secure/Strict 쿠키는 실제 HTTPS에서 검증해야 한다. B는 검증 제거가 아니며, C는 M1 사용자 결정과 RISK-0005 완화를 폐기한다. (NFR-09, PRD §10~§12, M1 회의록 §10, RISK-0005)

#### 가정

- M2 API가 아직 외부 소비자에게 배포되지 않았다.
- slug 변경 시 기존 URL redirect/alias는 M2 요구사항에 포함되지 않는다.
- 최초 배포 전에 HTTPS 환경과 RISK-0005 게이트 담당자가 마련된다.

#### 주요 이점

- 오류별 사용자 복구가 명확해지고 설정 데이터 손실·불필요한 로그아웃을 줄인다.
- 초기설정 안내와 실제 수정 기능이 일치한다.
- M2 가치와 무관한 runner 기반을 조기 고정하지 않으면서 배포 위험은 계속 추적한다.

#### 위험과 완화책

| 위험 | 영향 | 가능성 | 완화책 |
|------|------|--------|--------|
| 신규 코드가 문서·BE·FE·Swagger에서 불일치 | 잘못된 복구와 공개 계약 분기 | 중간 | status·code·message Controller/통합/FE 테스트 |
| slug 변경 후 공유 URL 404 | 사용자 링크 단절 | 중간 | M2 범위를 늘리지 않고 변경 결과를 명확히 안내, 후속 호환 정책은 별도 심의 |
| 배포 전 브라우저 게이트 미집행 | refresh·복구·signout 실패 | 중간 | RISK-0005 OPEN 유지, 배포 체크리스트에 증적을 차단 조건으로 연결 |
| 1440px 대조가 주관적 체크로 종료 | 디자인·카피 회귀 | 중간 | 세 화면 캡처와 차이 기록을 worklog에 남기고 독립 검증 |

#### 가장 강한 반대 논거

- Q1은 공개 오류 enum을 조기에 세분화하고, Q2는 UI 카피 정본을 바꾸며, Q3 B는 실제 브라우저 회귀를 M2에서 찾지 못한다. 그러나 기존 코드 재사용은 ADR-0003을 훼손하고, API 불변화는 카피 한 줄보다 훨씬 큰 계약 변경이며, 로컬 runner도 핵심 HTTPS 쿠키 계약을 입증하지 못한다.

#### 실패 시나리오

- 현재 비밀번호 불일치를 `AUTH_004`로 반환해 FE가 refresh/signin으로 이동하고 입력 내용을 잃는다.
- 불변 카피를 믿고 공유한 사용자가 Settings에서 slug를 바꾼 뒤 기존 URL이 404가 된다.
- RISK-0005가 문서에만 남아 최초 배포에서 Refresh 쿠키가 저장되지 않고 새로고침 후 세션이 사라진다.

#### 필수 변경 또는 필요한 정보

- 사용자에게 Q1=A, Q2=A, Q3=B를 `HIGH` 결정으로 승인받는다.
- 승인 후 NFR-04·PRD §4.4·§9, 디자인 원본·DESIGN-SYSTEM·화면 테스트를 동기화한다.
- RISK-0005를 OPEN으로 유지하고 배포 전 브라우저 smoke의 담당·시점·시나리오를 명시한다.

#### 근거가 확인된 사실

- **Q1=A.** `AUTH_001`은 signin 실패, `AUTH_004`는 Access 인증 필요, `BLOG_002`는 slug 중복, `BLOG_003`은 형식 오류로 이미 의미가 고정됐다. 현재 비밀번호 불일치와 완료 상태 충돌을 재사용 코드에 넣으면 도메인·복구 경계가 깨진다. (FR-SETTINGS-02·04, NFR-03·04, PRD §4.4·§5.2·§9.4-AB, ADR-0003)
- **Q2=A.** `PUT /blogs/me`의 명시적 slug 수정과 unique 검증을 불변으로 바꾸는 것은 카피 정리가 아니라 공개 API·비즈니스 규칙 변경이다. nickname 변경 시 자동 비연동과 사용자의 명시적 slug 변경은 구분해야 한다. (REQUIREMENTS §5, FR-SETTINGS-01·03·04, PRD §4.5·§5.2)
- **Q3=B.** NFR-09와 PRD §11~§12는 특정 runner를 요구하지 않는다. A는 신규 의존성이지만 로컬 HTTP로 핵심 운영 쿠키 계약을 검증하지 못하며, C는 승인된 게이트를 제거한다. (governance §2·§5, M1 회의록 §10, ADR-0003 §3, RISK-0005)
- A/A/B는 V1 변경 없이 현재 User·Blog, `ErrorCode`, principal 기반 서비스와 method 단위 공개 allowlist 안에서 구현 가능하다. (PRD §2.2·§4.3~§4.5·§10)

#### 가정

- M2 오류 코드는 외부 배포 전이다.
- 운영 동등 HTTPS 종단은 M2 동안 제공되지 않는다.
- 같은 사용자가 initial-setup을 동시에 두 번 호출할 수 있다.

#### 주요 이점

- 인증·User 검증·Blog 상태 충돌을 분리하고 기존 오류 계약을 보존한다.

- 신규 테스트 추상화를 조기 고정하지 않으면서 실제 HTTPS 게이트를 유지한다.

## 6. Codex 진행자 종합

### 합의점

- 세 검토자 전원이 서로 독립적으로 `APPROVE_WITH_CHANGES`, 확신도 94, 제안 위험 등급 `HIGH`를 제출했다.

- Q2에서 slug 수정 허용은 REQUIREMENTS의 저장·API 정책이고, 불변 카피는 사용자 승인으로 정합화해야 한다는 데 합의했다.

- 사용자 승인 전 구현·정본·공개 계약에 결론을 고정해서는 안 된다.

### 이견

최종 선택지에 대한 이견은 없다. 역할별 강조점은 다음과 같다.

- Product는 사용자 복구 분기와 slug 변경 후 공유 URL 단절을 강조했다.
- Architecture는 concurrent initial-setup의 단일 성공 보장과 DB unique 경쟁 매핑을 강조했다.
- Delivery & Risk는 디자인 원본·요약·구현의 동기화, 서버 확인 전 availability 표현 금지, 게이트별 증적을 강조했다.

### 확인된 사실

- FR-SETTINGS-04는 완료 후 재호출의 409를 명시하지만 NFR-04에는 전용 Blog 코드가 없다.
- `AUTH_001~004`와 `USER_004`는 ADR-0003과 PRD §9.4-AB로 의미가 고정돼 있다.
- FR-SETTINGS-03은 `url_slug` 수정과 형식·unique 검증을 명시하고 FR-SETTINGS-04는 완료 후 `/blogs/me` 수정 경로를 지정한다.
- 디자인 원본과 DESIGN-SYSTEM §8.6에는 “나중에 변경할 수 없어요”가 적혀 있다.
- M2에 Playwright/Cypress는 설치돼 있지 않으며 NFR-09·PRD §11~§12는 특정 runner를 요구하지 않는다.
- M1 회의록 정정 기록은 실제 브라우저 쿠키 검증을 최초 배포 전 필수 게이트로 이관했고 RISK-0005는 OPEN이다.
- 권고안은 V1·DB schema 변경을 요구하지 않는다.

- M2 오류 계약을 사용하는 외부 소비자가 아직 없다.
