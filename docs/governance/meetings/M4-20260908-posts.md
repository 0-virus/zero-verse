### Q1 — 글 저장·조회 계약

- JSON은 기존 camelCase. 경로는 명세의 `/api/v1/posts`, `/posts/{id}`, `/blogs/{blogId}/posts`, `/posts/drafts`, `/posts/{id}/images`, `/tags/{tagName}/posts`를 유지한다. slug 화면은 기존 공개 blog 조회의 id를 사용하며 중복 slug-list API를 추가하지 않는다.
- POST/PUT은 전체 편집 상태를 저장한다. categoryId 생략/null은 활성 DEFAULT로 귀속(기존 DB nullable은 유지). 동일 블로그 활성 DEFAULT/GENERAL/LOCKED 모두 선택 가능. 명시한 삭제/타 블로그 category는 CAT_001, 누락 blog는 BLOG_001, 타인 생성/수정/삭제는 POST_003을 제안한다.
- draft는 빈 제목 `""`과 빈 TipTap doc을 허용한다. 발행은 trim 후 제목 1~200자와 텍스트 또는 이미지가 있는 유효한 doc을 요구한다. 본문 JSON/HTML은 모두 검증하고 HTML은 서버 sanitize한다. 구체 payload/node 한도는 구현 전 BE가 제시해야 하며 미정 한도를 암묵적으로 발명하지 않는다.
- 태그는 trim+Locale.ROOT lower, 빈 항목 제거·중복 제거 후 최대10개, 각100자 이하(디자인·V1). title/URL/alt는 V1의200/500/255자 한도 내. 필수/형식 실패는 기존 VALIDATION_001. 동시 tag 생성은 DB unique를 최종 방어선으로 하며 transaction rollback-only를 무시하지 않는다.
- PUBLIC 발행은 익명, UNIVERSE 발행은 viewer→owner ACCEPTED, PRIVATE/draft는 작성자만. 목록/count/태그/이전다음에 동일 조건을 적용한다. 없는/삭제된 post·blog·owner는 POST_001; 존재하는 비공개 상세의 익명은 AUTH_004, 인증된 비허용자는 POST_002. drafts GET은 공개 wildcard보다 먼저 인증 강제한다.
- 목록은 page0/size20(max100), 기본 publishedAt desc/id desc. 인기순은 viewCount desc/publishedAt desc/id desc. categoryId/tag/visibility/publish 필터가 접근 조건을 넓히지 않는다. owner의 publish=false만 draft 목록 허용; 비소유자의 draft 요청은 POST_002(익명 AUTH_004). draft 목록 updatedAt desc/id desc.

### Q2 — 이미지 이력·조회수 DB

- PostImage soft delete를 유지한다. 다음 migration에서 M3와 같은 generated active_key를 추가해 `(post_id,display_order,active_key)` 활성 unique로 전환. 기존 V1은 수정하지 않는다. 이력 재사용 후 다운그레이드는 금지, 쓰기 중단/호환 앱/forward repair.
- images는 전체 snapshot, displayOrder는 중복 없는 0..N-1. post별 직렬화, 삭제 이력 보존, 순서 교환 시 임시 순서+flush→최종 순서 패턴 재사용. Post PUT과 image-only PUT이 교차해도 유효한 한 snapshot만 남는다. URL 소유 검증은 Q4 확정에 종속된다.
- 24시간 중복 방지는 재시작·동시 요청에서도 유지되도록 MySQL에 post/viewer-key/lastViewedAt의 최소 ledger를 추가한다. raw IP/UA는 저장·로그하지 않고 서버 키 기반 HMAC fingerprint를 사용한다. 접근 허용 후에만 ledger와 view_count를 한 transaction에서 원자 갱신한다. rolling24h이며 자정 초기화가 아니다. 만료 ledger 정리와 비밀키 rotation 영향은 운영 계획에 명시한다. Redis/인메모리-only 중복 방지는 제안하지 않는다.
- 이는 새 schema·개인정보 처리 설계이므로 사용자 승인 대상이다. ledger 상세 DDL/보유기간·정리 방식은 승인 전 기술 검토가 필요한 미결점으로 남긴다.

### Q3 — 에디터와 콘텐츠 보안

- TipTap3 React/PM/StarterKit/Image 사용. Link/Underline은 StarterKit 내장 재사용, TableKit과 공식 Markdown 확장만 추가 후보. 버전은 구현 시 같은 호환 버전으로 고정하고 beta Markdown 손실/XSS/표 round-trip을 필수 검증한다. 자체 Markdown parser·S3 signer·HTML sanitizer를 만들지 않는다.
- 디자인 toolbar의 밑줄/취소선/수평선/표/마크다운을 실제로 구현하려면 PRD §4.6 allowlist에 `u,s,hr,table,thead,tbody,tr,th,td` 및 안전한 정수 colspan/rowspan을 추가 승인한다. 임의 style/event/script/iframe/data/javascript URL은 계속 금지. BE는 OWASP Java HTML Sanitizer를 최소 새 의존성으로 사용한다.
- contentJson 원본을 안전하게 편집·복원하고 저장 HTML은 서버 정화한다. FE도 허용 노드/속성만 렌더하는 TipTap 경로를 사용하며 schema가 URL 안전성을 자동 보장한다고 가정하지 않는다. JSON과 HTML 내용 불일치 시 처리 기준도 검토한다.
- 대안: 표·마크다운을 M4에서 제외하려면 디자인·범위 변경의 별도 사용자 승인이 필요하다. 승인 없이 버튼만 남겨 가짜 동작으로 처리하지 않는다.

### Q4 — 업로드 보안과 공개 이미지 경계(종속 단계 보류 가능)

- local은 LocalStack + loopback endpoint + path-style, 운영은 S3 직접 URL. AWS SDK for Java2 S3Client/S3Presigner만 추가하고 실제 credentials는 로컬 비추적 설정/환경으로 받는다. 버킷/정책 변경 및 비용 유발 작업은 별도 승인 전 하지 않는다.
- 기존 요청 fileName/contentType/purpose에 fileSize를 추가하고 1..5,242,880bytes, 네 MIME만 허용하는 안이다. UI10MB 문구는5MB로 정합화한다. 서버가 userId/purpose/UUID 기반 key를 생성, 5분 PUT 서명과 publicUrl·필수headers·expiresAt를 반환한다. FE는 직접 업로드 성공 후에만 URL을 첨부한다.
- fileSize 자기신고와 FE 검사만으로 서버 크기 제한이 충족되지는 않는다. PUT의 signed Content-Length/Content-Type과 실제 브라우저 파일 크기 변경 실패를 먼저 입증해야 한다. 입증 불가 시 fail-open하지 않고 POST policy 등 계약 변경을 재심의한다. 저장 전 서버는 설정된 bucket/key의 HEAD로 존재·크기·MIME·자기 user/purpose 경계를 확인한다. 임의 외부 URL을 서버가 fetch하지 않는다.
- HEAD MIME은 실제 파일 내용 판별이 아니고 서명 URL도 일회용이 아니다. MIME 위장·만료 전 overwrite의 보장 수준/추가 대책은 기술 검토에서 명확히 한다. 체크섬 서명 등 필요한 대책을 비용·실측 근거 없이 완료로 가정하지 않는다.
- **공개 S3 URL은 글의 PRIVATE/UNIVERSE 접근제어와 별개다.** 기존 publicUrl 계약을 유지하면 URL을 아는 제3자의 이미지 조회와 글 삭제 후 URL 접근이 남는다. 이를 수용할지, 비공개 bucket+권한 확인 후 짧은 GET URL로 변경할지 사용자가 결정해야 한다. 후자는 CloudFront 없이도 가능하지만 URL 반환/본문 렌더링/만료 계약의 추가 설계가 필요하다. 이 선택 전 Q4 구현·배포를 승인하지 않는다.

### Q5 — 화면 범위와 인수

- 상세 메타에 PRD §9.3대로 조회 N 추가. 대표 이미지는 URL 저장과 에디터 하단 발행 설정 카드 내 업로드/미리보기/제거를 제안한다. 상세 상단에 별도 hero는 추가하지 않고 본문 이미지만 표시(명시 승인 필요).

범위는 승인된 이미지 방향의 구체화다. Q1 게시글 전체 DTO·Q2 조회수 ledger·Q3 전체 콘텐츠·Q5 전체 화면 계약의 승인이 아니다. 이 §11을 동일 근거와 함께 새 독립 심의한다. 아래 숫자·새 API·소유권/캐시·추가 의존성은 아직 사용자 확정 값이 아니다. 2026-09-09 v2 초안 작성자는 root이며 BE/FE는 기술 입력 기여자, 최종 검토자는 별도 컨텍스트다.

**결정할 질문:** 60초 서명 GET의 잔여 접근 창, 아래 업로드 보조 표/API·형식 검증·정리 계약을 승인하고 U0 로컬 안전성 검증부터 진행할 것인가? A(권고)는 아래 v2, B는 즉시 철회가 필요할 때 매 요청 인증 프록시로 재설계하는 대안이며 B의 구현·인프라는 이번 안에 포함하지 않는다. 어느 쪽도 M4 전체 구현/외부 게시/AWS 운영 변경 승인을 자동 포함하지 않는다.

### 11.1 저장 주소와 표시 주소

- 기존 `profileImageUrl`, `thumbnailUrl`, `PostImage.imageUrl`, TipTap `image.src`/정화 HTML에는 서버가 발급한 **무서명 canonical S3 URL**만 저장한다. 현행 URL500 필드 유지; object key에는 서버가 만든 불투명 식별자를 사용한다. `publicUrl`이라는 이름/영구 공개 의미는 철회한다. 서명 쿼리·fragment·userinfo·외부 host·비정상 path·data/blob/javascript URL은 영구 참조로 받지 않는다. 임의 URL을 backend가 fetch하지 않는다.
- 실제 bucket은 비공개다. 무서명 URL을 아는 것은 읽기 권한이 아니다. API는 configured bucket/key를 canonical URL과 정확히 매핑하며 단순 startsWith 검사를 하지 않는다. LocalStack의 지정 loopback/path-style만 로컬 예외, 운영은 HTTPS와 지정 S3 host만 허용한다.
- 화면은 아래 resolver가 준 `displayUrl`과 `expiresAt`만 메모리에서 사용한다. 기존 domain 응답의 canonical 문자열 의미는 유지하며 모든 기존 소비처(설정 프로필, AuthContext 사용자 DTO, blog owner/hero, 새 목록 thumbnail, 상세/편집 본문)를 함께 연결한다. signed URL을 DB·JSON/HTML 원본·local/sessionStorage·로그에 저장하지 않는다.

### 11.2 권한 재검사와 URL 만료

- 새 `POST /api/v1/uploads/read-urls`: `{ imageUrls: string[] }`, 1..50개 고유 canonical URL. 선택적 Access Token, 공통 응답 `data.items[{imageUrl,displayUrl,expiresAt}]`를 입력 순서로 반환한다. 모두 권한 확인 후 발급하며 한 항목이라도 실패하면 전부 실패한다. 업로드/완료/도메인 쓰기와 별개로 읽기 전용 resolver다. URL 발급 때문에 글 상세를 재조회하거나 조회수를 증가시키지 않는다.
- **글에 연결된 이미지**: 해당 post·blog·owner가 삭제되지 않았고, PUBLIC 발행/UNIVERSE viewer→owner ACCEPTED/PRIVATE 및 draft 작성자 전용이라는 같은 predicate를 통과해야 한다. 과거 연결 이력이나 다른 공개 글의 접근권으로 대신 허용하지 않는다. 작성자 SUSPENDED의 기존 공개 글은 계속 공개하되 신규 업로드/저장은 ACTIVE 재검사한다.
- **프로필**: soft delete되지 않은 사용자의 현재 `profileImageUrl`로 실제 연결된 프로필 이미지만 공개한다(SUSPENDED를 삭제로 간주하지 않음). 글 이미지 purpose를 프로필에 연결하지 않는다. READY 미첨부 이미지 preview는 소유자에게만 허용하며, 삭제·정리 중인 이미지는 누구에게도 새 URL을 발급하지 않는다. BOUND 후 떼어낸 이미지는 같은 살아 있는 글의 소유자 또는 같은 프로필 소유자만 grace 내 preview/재연결할 수 있다. 이는 프로필에 post predicate를 적용한다는 뜻이 아니다.
- GET 서명 유효기간은 발급 시점부터 **60초**를 제안한다(자격증명 수명이 더 짧으면 먼저 만료). 새 발급 때 현재 권한을 매번 확인한다. URL 응답과 S3 객체 응답은 `Cache-Control: private, no-store`; GET 요청은 앱 토큰/쿠키를 S3에 보내지 않고 이미지 referrer도 보내지 않는다.
- **한계**: signed GET은 소지자에게 권한을 주는 bearer URL이다. 발급 후 비공개 전환/연결 해제/삭제 시에도 남은 유효기간 안에 시작된 요청은 성공할 수 있고, 만료 전에 시작된 다운로드는 이후에도 끝날 수 있다. 내려받은 바이트/스크린샷을 회수할 수 없다. 즉시 회수가 필수라면 매 요청 인증을 수행하는 API 바이트 프록시로 별도 변경해야 한다. 이번 권고는 그 비용 대신 60초 발급 창의 잔여 위험을 명시적으로 승인받는 안이다.

### 11.3 편집·실패·오래 열린 화면

- 에디터의 저장 원본은 canonical `image.src`를 유지하고 표시만 NodeView/읽기 전용 renderer의 별도 메모리 map으로 해석한다. 서명 갱신으로 editor document/undo/dirty/savedAt을 변경하지 않는다. 새 파일의 `blob:` preview는 로컬 미리보기 전용이고 서버 완료 전 저장 성공으로 표시하지 않는다.
- 화면 진입/새 이미지/재노출에 필요한 항목만 batch 발급한다. 무조건 60초 polling하지 않는다. 이미지 onError는 현재 화면·viewer·참조 세대가 같은 경우 한 번만 재발급하고, 실패/403/404는 재시도 UI 또는 기존 avatar fallback을 표시한다. 글 본문·폼 내용은 유지한다. 재발급으로 깨진 이미지가 무한 반복되지 않도록 두 번째 실패는 사용자 재시도까지 중단한다.
- 로그아웃·사용자/글 전환 시 map과 진행 요청을 폐기하고 늦은 응답을 무시한다. 비공개 화면은 기존 route/auth 정책대로 가리며, 이미 취득한 이미지의 브라우저 외부 회수는 보장하지 않는다. 자동 본문 저장이나 이미지 업로드를 위한 숨은 draft 생성은 이 안에 포함하지 않는다.

### 11.4 업로드·연결·정리

**권고: 단일 `image_uploads` 보조 표 + 변경 불가능한 객체 + 최초 연결 유지.** 미디어 라이브러리/별도 서비스/선행 draft 생성은 만들지 않는다. 기존 URL 필드는 그대로 둔다. 현재 URL 컬럼만 검색하는 무스키마 안은 thumbnail 교체 후 옛 주소의 원래 글을 잃으므로 철회한다. 표 한 개로 완료 검증, 재시작, 아직 저장하지 않은 글의 preview, 다른 글 재사용 거부, 정리 경쟁을 같은 행에서 다룬다. 이는 새 DB 계약이므로 사용자 승인 대상이다.

#### 업로드 API와 바이트 검증

1. 기존 `POST /api/v1/uploads/presigned-url` 요청은 `{fileName,contentType,fileSize,purpose,checksumSha256}`. fileName은 표시 입력이며 key에 사용하지 않는다(1..255자, 제어문자 금지). type은 기존 jpeg/png/webp/gif, fileSize는 정수 1..5,242,880 bytes, SHA-256은 32바이트의 표준 Base64 문자열이다. 서버는 현재 ACTIVE 사용자 확인 후 `users/{ownerId}/{purpose}/{uuid}.{확정타입확장자}` key와 PENDING 행을 만들고 `{imageUrl,uploadUrl,headers,expiresAt}`를 반환한다. imageUrl이 canonical 저장 참조다. PUT은 생성 후 5분까지만 유효하며 같은 key를 재발급하지 않는다.
2. SigV4 PUT에는 예상 Content-Length, Content-Type, `If-None-Match:*`, `x-amz-checksum-sha256`, `Cache-Control: private, no-store`를 묶는다. 응답 headers에는 브라우저가 설정할 헤더만 포함하고 Host/Content-Length는 브라우저가 생성한다. SDK가 실제 서명한 길이와 헤더를 검사한다. raw File PUT 성공, 크기·헤더·checksum 변조 거부, 동일 key overwrite 거부를 먼저 실측하지 못하면 uploader를 완료로 승인하지 않는다. 검증 실패를 무서명/길이 미검증 PUT이나 자체 POST signer로 우회하지 않는다.
3. 새 `POST /api/v1/uploads/complete` 요청 `{imageUrl}`. 소유자 ACTIVE 확인 후 configured S3 HEAD에서 객체 존재·실제 크기·metadata·checksum을 기대값과 대조한다. 최대 5,242,881 bytes의 제한된 GET으로 SHA-256을 재검증하고 MIME를 내용으로 판별한다. 판별은 승인 대상 `org.apache.tika:tika-core`의 MIME detector(파일명/Content-Type hint 없는 입력)만 사용하며 전체 parser bundle/자체 magic parser는 추가하지 않는다. jpeg/png/webp/gif 이외, 선언과 다른 형식, 빈 파일/과대·checksum 불일치는 거부한다. 확장자/HEAD type만으로 통과하지 않는다. 이것은 **형식 식별**이지 모든 손상 이미지의 완전한 디코딩·malware/EXIF 제거 보장이 아니다.
4. 검증 성공 후 READY로 전이하고 `{imageUrl}`를 반환한다. 중복 complete는 같은 검증된 불변 객체에 대해 멱등 성공한다. 검증 전 PENDING·검증 실패·DELETING/DELETED에는 preview GET/도메인 저장을 허용하지 않는다. 실패한 객체는 읽기 금지 상태로 보존했다가 PUT 만료 뒤 정리한다. S3 직접 PUT 412/409나 응답 손실은 저장 성공으로 간주하지 않고 complete 검증 또는 새 UUID 업로드로 회복한다.

#### 최소 DB 표현과 원자 연결

다음 가용 forward migration을 사용하며 V1/V2는 수정하지 않는다. 컬럼명은 아래 안으로 심의한다.

| 컬럼 | 타입·제약 | 의미 |
|------|-----------|------|
| id | CHAR(36) ASCII binary PK | 서버 UUID |
| owner_id | BIGINT NOT NULL FK users | 업로드 소유자, 불변 |
| purpose | VARCHAR(32) NOT NULL CHECK 3가지 enum | 프로필/대표/본문 용도, 불변 |
| image_url | VARCHAR(500) ASCII binary UNIQUE NOT NULL | canonical URL, 불변 |
| expected_size | BIGINT NOT NULL CHECK 1..5242880 | 서명 크기 |
| content_type | VARCHAR(32) NOT NULL CHECK 허용4종 | 검증해야 할 타입 |
| checksum_sha256 | BINARY(32) NOT NULL | 기대 SHA-256 |
| status | VARCHAR(16) NOT NULL CHECK PENDING/READY/BOUND/DELETING/DELETED | 파일 검증·연결·정리 상태 |
| post_id | BIGINT NULL FK posts | 글 이미지의 최초 연결, 한 번 설정 후 변경 금지 |
| created_at | DATETIME(6) NOT NULL | UTC 생성, PUT 만료=생성+5분 |
| unreferenced_at | DATETIME(6) NULL | 미첨부 생성 시 created_at, live 연결 시 null, 마지막 연결 해제 시 현재 시각 |
| updated_at | DATETIME(6) NOT NULL | 전이/정리 상태 기록 |

- 인덱스는 unique image_url 및 `(status,unreferenced_at)` 정리 검색, FK용 owner/post로 제한한다. PROFILE_IMAGE는 post_id가 항상 null, BOUND인 POST_*는 post_id NOT NULL이라는 CHECK를 둔다. DELETING/DELETED도 과거 post_id를 보존한다. DB에는 이미지 바이트·서명 URL·원본 파일명을 저장하지 않는다.
- 최초 글 저장에서 blog→post→관련 image_uploads(id 정렬) 행 잠금을 잡아 READY를 BOUND로 바꾸고 post_id를 기록한다. PostImage·thumbnail·contentJson/contentHtml 저장과 같은 DB transaction이다. 실패 시 전체 rollback하며 업로드 파일/READY는 남겨 사용자가 재시도할 수 있다. 모든 Post category_id 쓰기는 기존 ADR-0005 blog lock/활성 카테고리 재검사를 유지한다.
- 프로필 변경은 해당 user→관련 image_uploads(id 정렬) 잠금, 현재 사용자의 PROFILE_IMAGE만 연결한다. 모든 binder는 소유자·purpose·상태·canonical 일치 및 실제 도메인 쓰기 권한을 검사한다. BOUND POST_*는 **같은 post_id만** 재사용하고, 다른 글 또는 프로필로 옮기는 것은 떼어낸 뒤에도 거부한다. 다른 글에서 쓰려면 새 파일 업로드가 필요하다. 새 user 전역 lock을 모든 category/post 경로에 추가하지 않는다.
- body 원본의 canonical 이미지 집합과 active PostImage 연결은 일치해야 한다. image-only PUT도 원본/연결 불일치를 만들면 거부하며, 정확한 전체 Post payload/오류와 배열 의미는 Q1/Q3 후속 계약에서 닫는다. 현재 활성 연결이 없거나 post/blog/owner가 삭제되면 과거 BOUND 행만으로 공개 URL을 발급하지 않는다.
- URL-only read batch는 image_url UNIQUE 행에서 **서버가 owner/purpose/최초 post_id를 결정**한 뒤 현재 도메인 연결을 정확히 대조한다. 클라이언트가 보낸 resource ID나 URL prefix를 권한의 근거로 믿지 않는다. 연관 없는 key, legacy 미등록 URL, 서명 쿼리 URL은 거부한다. 기존 외부 프로필 URL은 자동 수집/이관하지 않고 표시 fallback과 재업로드 안내를 제공하며, URL을 변경하지 않은 다른 프로필 수정은 기존 값 유지가 가능하도록 후속 DTO 회귀로 보장한다.

#### 정리·경쟁·오류

- READY/PENDING 미첨부, 또는 BOUND에서 마지막 활성 연결이 해제된 객체는 24시간 grace를 둔다. 활성 draft의 연결은 만료 대상으로 삼지 않는다. 24시간 이상 저장하지 않은 업로드가 정리됐다면 에디터 원문을 유지하고 파일 재선택/업로드를 안내한다.
- 애플리케이션의 단순 시간별 작업이 오래된 미참조 행을 최대200개씩 찾는다. 각 asset 행 lock 아래 최신 상태·도메인 활성 참조를 확인하고 DELETING으로 먼저 DB commit한 후 해당 configured S3 key만 삭제한다. binder는 DELETING을 거부하므로 삭제와 새 연결이 경합해도 live 객체가 지워지지 않는다. cleaner는 asset lock을 잡은 채 user/blog/post lock을 추가 획득하지 않는다. 실패는 DELETING 유지·다음 실행 재시도, 성공은 DELETED; 성공 후30일이 지나면 보조 표의 tombstone만 정리할 수 있다. key는 재사용하지 않는다. owner/blog/post soft delete도 정리 후보 판정에 반영한다(BOUND의 unreferenced_at이 null이어도 연결 리소스의 deleted_at+24h 경과를 별도 후보로 조회). 검사 transaction은 READ_COMMITTED로 최신 참조를 읽고, soft delete 후 재연결은 binder에서 거부한다. live URL은 lifecycle 일괄 삭제 대상에 넣지 않는다.
- DB와 S3를 한 원자 transaction이라고 주장하지 않는다. 앱 재시작/삭제 실패/complete와 binder·cleaner 경쟁을 실제 MySQL+LocalStack으로 검사한다. 운영 데이터 삭제/버킷 정책 적용은 별도 배포 권한을 따른다.
- 기존 `AUTH_004`(401), `USER_001/003`, `POST_001/002/003`, `UPLOAD_001`(타입), `UPLOAD_002`(초과), `VALIDATION_001`(입력 형식)을 유지한다. 새 `UPLOAD_003`(400, `유효하지 않은 이미지 참조입니다.`), `UPLOAD_004`(409, `이미지를 연결할 수 없는 상태입니다.`)를 제안한다. pending/다른 글에 bound/정리 중 충돌은004, 미등록·canonical/소유자/purpose 불일치는003이며 남의 자산 존재/파일 내용을 에러에 노출하지 않는다. storage 장애는 고정 `COMMON_500`, 저장된 글/폼을 성공으로 표시하지 않는다. read batch의 비공개 글 무권한은 익명 AUTH_004/인증 POST_002, 삭제된 글 POST_001이다.

### 11.5 확인한 1차 자료와 미검증 경계

- [AWS presigned URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html): bearer·만료 전 재사용·요청 시작 시 만료 검사. 위 60초는 AWS의 의무값이 아니라 이 초안의 권고다.
- [AWS 조건부 쓰기](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html): SigV4 `If-None-Match:*` PUT은 존재하는 key 덮어쓰기를 거부한다. 삭제/version delete marker 이후 재업로드 가능성까지 고려해야 하며 이름만 UUID라고 일회용이 되지 않는다.
- [AWS checksum](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html): 지정 checksum과 실제 바이트의 일치를 검사한다. 이는 MIME 판별/바이러스 검사와 다르다.
- [MDN 금지 요청 헤더](https://developer.mozilla.org/en-US/docs/Glossary/Forbidden_request_header): 브라우저의 Content-Length는 JS가 임의 설정하는 헤더가 아니다. signed length를 쓴다면 실제 File 전송에서 자동 생성되는 값과 일치하고 변조가 실패하는지 별도 실측해야 한다.
- [AWS Java2 S3Presigner](https://docs.aws.amazon.com/java/api/latest/software/amazon/awssdk/services/s3/presigner/S3Presigner.html): SDK 서명기 재사용. POST policy를 이미 지원하는 Java 메서드가 있는 것으로 가정하지 않는다.
- [Apache Tika detection](https://tika.apache.org/3.2.1/detection.html): 내용 기반 형식 판별과 이름/Content-Type hint는 다르다. 새 MIME 판별 의존성을 선택해도 파일 안전성/완전한 디코딩을 증명하지는 않는다.
- 이번 작업은 문서 계약 보완이다. 실제 LocalStack/AWS 업로드, signed headers/CORS, negative size/type/replay, 만료/권한 경쟁은 아직 실행하지 않았다. 구현 승인 후 이 검증을 먼저 수행하고 실패 시 해당 업로드 경로를 닫는다.
- 2026-09-09 추가 확인: [LocalStack 공식 2026.03.0 발표](https://blog.localstack.cloud/localstack-for-aws-release-2026-03-0/)와 [설치 문서](https://docs.localstack.cloud/aws/getting-started/installation/)는 2026-03-23 이후 통합 AWS 이미지가 auth token을 요구한다고 명시한다. `LocalStack=계정 없이 항상 무료`를 전제하지 않는다. U0 실행에는 사용자가 허가한 계정/토큰·라이선스 조건 또는 별도 승인한 지원 가능한 구버전이 필요하다. 계정 생성·구매·만료된 우회 플래그·보안/동작 불확실한 임의 다운그레이드는 자동 실행하지 않는다. 이 자료는 진행 중 세 reviewer에게 같은 사실 입력으로 추가 배포한다.
- 추가 U0 재현 조건: [LocalStack S3 설정](https://docs.localstack.cloud/aws/customization/configuration-options/#s3)의 기본값은 presigned 서명/만료 검증을 생략한다. 검증 실행은 `S3_SKIP_SIGNATURE_VALIDATION=0`으로 고정하고, 일반 SigV4/바이트 검증은 `S3_VALIDATE_SIGNATURES=1` 및 실제 선택 버전의 지원 credentials/설정을 확인한다. 잘못된 signature·만료 URL·무서명 private GET이 실제 실패하는 negative를 남겨야 하며, 플래그를 넣었다는 사실만으로 보안 검증 통과라 하지 않는다. 계정 token과 테스트 AWS 자격증명은 서로 다른 값이며 둘 다 비밀/용도 경계를 지킨다.
