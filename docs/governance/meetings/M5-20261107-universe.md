## 1. 결정할 질문

M5에서 V1 스키마를 유지하고 결정적 사용자 쌍 잠금으로 FR-UNI-01~11을 구현하면서, BlogPage 관계 액션용 보호 snapshot API와 `UNI_004/005` 오류를 추가하는 최소 계약을 채택할 것인가?

## 2. 배경과 범위

### 배경

- REQUIREMENTS §4/§6.6은 단방향 `PENDING/ACCEPTED/BLOCKED`, hard delete와 FR-UNI-01~11 endpoint를 정한다.
- PRD §5.6/§7/§10은 backend 관계 CRUD·목록과 SettingsUniversePage/BlogPage 액션을 M5에 둔다.
- V1에는 `(from_user_id,to_user_id)` unique와 self-check가 있고 M4는 ACCEPTED 방향성만 읽는다. 실제 관계 CRUD와 FE 동작은 없다.
- 현재 NFR-04에는 자기자신/중복/차단(`UNI_001~003`)만 있어 request/relationship 없음·권한·잘못된 상태를 표현할 계약이 없다.
- BlogPage는 대상 owner ID를 알지만 현재 관계를 한 건으로 조회할 API가 없다. 전체 목록 조합은 페이징 때문에 정확하지 않고 공개 blog DTO 개인화는 공개 응답 캐시·정보 노출 경계를 바꾼다.
- 새 clone에는 gitignore 대상 디자인 원본이 없어 PRD 요약만 존재한다. 정확한 UI 대조는 원본 복구가 필요하다.

### 포함 범위

- FR-UNI-01~11, 관계 snapshot, `UNI_004/005`, 공통 response/page, Swagger.
- 결정적 pair lock, 동시 신청/수락/차단/삭제 안전성, hard-delete 재신청.
- SettingsUniversePage 전체 목록·mutation과 BlogPage 관계 액션.
- 신청→수락→M4 UNIVERSE 글 접근 통합 검증.

### 제외 범위

- M6 댓글/좋아요 구현, M7 feed/search, M8 알림 row 생성, S3/U0, 신고/RSS.
- V1 수정, 새 외부 의존성, 실명/email/birthDate 노출.

### 제약

- 모든 Universe API는 인증 필수다.
- 차단은 양방향 PENDING/ACCEPTED 제거 후 차단자→대상 BLOCKED를 유지한다.
- 상대의 차단 사실은 snapshot에서 `UNAVAILABLE`로 일반화한다.
- 목록 `page=0,size=20,max=100`, nickname 검색, 공통 `PageResponse`.
- 시각 정본 복구 전 최종 UI PASS 금지.

## 5. 독립 검토

### Product Reviewer

- 권고 `APPROVE_WITH_CHANGES`, 확신도 88, 위험 `HIGH`.
- A는 M4의 UNIVERSE 글 접근을 실제 관계 UX로 연결하고 B의 page 누락, C의 공개 DTO 개인화 위험을 피한다.
- 필수 보완은 양방향 PENDING·부분 ACCEPTED 조합을 모두 표현하는 방향별 snapshot, canonical mutation 후 재조회, 관계 DTO의 `bio/name/email/birthDate` 비노출, 디자인 원본 복구다.
- 가장 강한 반론은 snapshot 상태표가 불완전하면 새 endpoint가 오히려 잘못된 CTA를 공식화한다는 점이다.
- 대표 실패 경로는 양방향 PENDING에서 단일 `OUTGOING_PENDING`만 반환해 incoming 수락을 숨기는 경우다.

### Architecture Reviewer

- 권고 `APPROVE_WITH_CHANGES`, 확신도 93, 위험 `HIGH`.
- V1 FK/unique/CHECK는 충분해 migration 없이 구현할 수 있으나 모든 mutation이 사용자 ID 오름차순 pair lock과 lock 후 양방향 재조회를 공유해야 한다.
- snapshot은 단일 enum 대신 `availability`, `outgoing`, `incoming`을 반환하고 각 PENDING 방향의 `requestId`를 제공해야 한다.
- `UNI_004`는 부재/비소유 동일 404, `UNI_005`는 존재하지만 상태 전이 불가 409로 고정한다. 삭제 경쟁으로 행이 먼저 사라지면 404다.
- 가장 강한 반론은 snapshot이 즉시 stale할 수 있고 pair lock을 일부 경로가 우회하면 deadlock/`COMMON_500`이 생긴다는 점이다.
- 대표 실패 경로는 수락과 차단이 다른 lock 순서를 사용해 ACCEPTED가 남고 M4 UNIVERSE 글 접근이 계속 열리는 경우다.

### Delivery & Risk Reviewer

- 권고 `APPROVE_WITH_CHANGES`, 확신도 90, 위험 `HIGH`.
- 계약→mutation/동시성→목록/snapshot→FE API→화면→통합 QA 순으로 분할하고, M4 기준선과 실제 MySQL 경쟁·HTTP/OpenAPI·1440px을 다시 검증해야 한다.
- 개인화 snapshot은 `Cache-Control: private, no-store`, 안정 정렬 `updatedAt,id`, active/non-deleted 사용자 join과 큰 offset 방어를 요구한다.
- rollback 시 ACCEPTED 데이터가 남아 M4 접근 predicate가 계속 열릴 수 있으므로 코드 롤백과 데이터 보존 경계를 문서화해야 한다.
- 가장 강한 반론은 A가 B보다 일정·검증 비용이 크다는 점이나, B의 page 누락을 받아들이려면 BlogPage 액션 자체를 후속으로 명시 이관해야 한다.
- 대표 실패 경로는 snapshot에 request ID가 없어 수락/거절/취소가 동작하지 않거나, 디자인 원본 없이 기능 테스트만 통과하고 시각 DoD를 오판하는 경우다.

## 6. 진행자 종합

세 검토자는 모두 A를 `APPROVE_WITH_CHANGES / HIGH`로 권고했다. B는 페이징된 목록의 page 밖 관계를 놓쳐 정확한 BlogPage 액션을 만들 수 없고, C는 공개 blog 응답을 Authorization별로 개인화해 캐시·차단 정보 경계를 확대한다.

진행자 최종 권고는 아래 **A-v2**다.

1. V1과 `(from_user_id,to_user_id)` unique를 유지하고 migration을 추가하지 않는다.
2. 모든 mutation은 actor/target 사용자 행을 ID 오름차순으로 lock한 뒤 양방향 Universe row를 다시 읽는다. block은 양방향 PENDING/ACCEPTED를 delete+flush한 뒤 actor→target BLOCKED를 생성/유지하고 상대의 BLOCKED는 보존한다.
3. `GET /api/v1/universe/relationship/{targetUserId}`를 인증 필수 `FR-UNI-12`로 추가한다. `Cache-Control: private, no-store`를 사용한다.
4. snapshot payload는 `target{id,nickname,profileImageUrl,blogSlug}`, `availability=AVAILABLE|BLOCKED_BY_ME|UNAVAILABLE`, `outgoing{status=NONE|PENDING|ACCEPTED,requestId}`, `incoming{status=NONE|PENDING|ACCEPTED,requestId}`다. 상대가 나를 차단한 사실은 `UNAVAILABLE`로만 반환한다. 양방향 PENDING과 부분/양방향 ACCEPTED를 두 방향 필드로 손실 없이 표현한다.
5. `UNI_004`/404는 요청·관계 부재 또는 caller 비소유를 동일 메시지로 숨긴다. `UNI_005`/409는 row가 존재하지만 현재 상태에서 전이 불가한 경우다. lock 전에 존재했어도 경쟁으로 먼저 hard delete됐다면 최종 재조회 기준 `UNI_004`다.
6. actor가 SUSPENDED이면 새 mutation을 `USER_003`으로 거부한다. target SUSPENDED만으로 기존 관계나 공개 blog를 삭제·숨기지 않으며, soft-deleted target은 `USER_001`이다. 목록은 soft-deleted 사용자를 제외하고 suspended 관계는 status를 노출하지 않은 최소 DTO로 유지한다.
7. Blog hero의 단일 주 액션 우선순위는 `BLOCKED_BY_ME 해제` → `UNAVAILABLE 비활성` → `incoming PENDING 수락` → `outgoing PENDING 취소` → `outgoing ACCEPTED 연결 끊기/FRIEND 연결됨` → `NONE 또는 follower 신청`이다. 동시에 가능한 나머지 동작은 SettingsUniversePage에서 제공한다.
8. 알림 row 생성은 M8, RSS·신고는 M5에서 제외한다. M5 mutation이 notification row를 만들지 않는 것을 검증한다.

공개 API·NFR-04·접근제어 변경이므로 최종 등급은 `HIGH`, 사용자 승인 전 제품 구현은 보류한다. 디자인 원본 부재는 backend 계약 승인과 구현을 막지는 않지만 최종 FE 시각 PASS와 M5 완료를 막는다.
