# ZeroVerse CI/CD Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` at implementation time. 프로젝트 역할 소유권·독립 QA·사용자 승인 규칙이 우선한다. 아래 체크박스는 계획이며 완료 표시가 아니다.

**Goal:** PR 자동 검증과 main 릴리스 생성, 사용자 승인 후 Lightsail이 검증된 패키지를 가져오는 운영 배포를 구성한다.

**Architecture:** GitHub-hosted runner에서 테스트·빌드를 마치고 정확한 artifact ID로 패키지를 보관한다. 승인된 main workflow가 배포 요청과 요청 증거를 만들고 종료하면, Lightsail의 제한된 systemd 서비스가 이를 검증·적용하고 GitHub Deployment 상태를 보고한다. 운영 서버에 Actions runner를 설치하거나 외부 배포 포트를 열지 않는다.

**Tech Stack:** GitHub Actions/Environments/Deployments/Artifacts, GitHub App, Ubuntu 24.04, Java 21, Node 22, Python 3 표준 라이브러리·OpenSSL, 기존 Caddy/systemd/MySQL/Flyway.

**Spec:** 사용자 방향 선택과 이 문서 §1~7. 기존 운영 계약은 [배포 회의 §10·15](X-20261113-deployment.md), [ADR-0009](../decisions/ADR-0009-deployment-s3-contract.md), [운영 가이드](../../../deploy/README.md)를 따른다.

- 회의 ID: `X-20261117-cicd`
- 작성일/진행자: 2026-11-17 KST / Codex root
- 상태: **방향 승인·상세 계획 작성 / 구현·GitHub 설정·서버 활성화 미실행**
- 사용자 선택: “CI는 자동, 운영 배포는 직접 선택하고 서버가 패키지를 가져오는 방식”에 “그렇게 해줘. 계획 세운 뒤 가이드라인도 제시해줘”. 이는 이번 계획·가이드 작성 지시이며 상세 인프라 변경 실행 승인은 아니다.

확인한 기준은 main `62d241e`, 공개 GitHub 저장소 `0-virus/zero-verse`(repository ID `1253062454`), `.github/workflows` 미존재다. Java 21/Testcontainers MySQL 테스트, 프론트 test/lint/build, `deploy/release.py` 패키징/검증, 암호화 백업은 이미 있다. 운영은 서울 Lightsail 2GB·Caddy·systemd·Aiven·private S3다. 최근 로그아웃 변경은 커밋됐지만 운영 배포되지 않았다. 이전 BE670/FE504 결과는 기준 이력이며 새 CI의 실제 통과로 간주하지 않는다.

- 포함: CI, 동일 artifact 배포, 승인·출처 검증, pull agent, 백업과 배포의 상호 배제, 실패 복구, 운영 가이드와 격리 인수.
- 제외: 제품 API/DB 변경, Docker/ECS/Kubernetes 전환, 운영 서버에서 CI 실행, 자동 main 배포, 무중단 SLA, 운영 데이터로 PR 테스트, S3 정리, DB 자동 복원, 외부 백업 자동 복제.

## 2. 선택지와 결정의 경계

| 방식 | 이점 | 비용·위험 | 판단 |
|---|---|---|---|
| A. hosted CI + 승인 후 서버 pull | 기존 SSH 제한 유지, 운영 비밀을 CI로 옮길 필요 없음 | 요청 검증·상태 보고·복구 도구 구현 필요 | **사용자 선택 방향** |

## 3. Global Constraints

- 운영 서비스 `zeroverse`/`caddy`, 도메인 `zeroverse.co.kr`, release 루트 `/opt/zeroverse/releases`, current `/opt/zeroverse/current`를 유지한다.
- Java 21, Node 22(최소22.12), `ubuntu-24.04` VM runner. 정확한 patch/tool 버전과 이미지 정보는 실행 증거에 남긴다. Gradle wrapper와 `npm ci`/lockfile을 사용한다.
- 운영 DB/AWS/JWT 비밀·SSH 개인키·백업 복호화 키를 Actions에 넣지 않는다. PR job은 운영 네트워크·운영 자격증명 없이 실행한다.
- 배포 package는 검증된 JAR·FE·명시 파일만. 서버에서 build하지 않으며 다운받은 `ops/` 스크립트를 root로 실행하거나 자동 설치하지 않는다. 설치 도구 갱신은 별도 검토·수동 설치다.
- 사용자 자료·기존 local DB/업로드 보존. 코드/Git 설정/서비스 변경은 승인한 해당 단계에서만 한다.
- 최초 CD 버전은 **Flyway SQL·Java migration 및 고정 helper 파일 집합·각 SHA256이 현재 release와 같고 운영 history가 일치하는 배포만 허용**한다. 새 migration·migration 코드 변경·기존 history 불일치는 자동 적용하지 않는다. 제품 데이터 변환·비호환 설정 변경 역시 이 경로에서 제외한다.
- 단일 서버의 짧은 점검 시간 허용. reverse migration·자동 DB dump 복원·pre-S3 JAR 복귀 금지.
- 기존 매일04:00 KST/정기7일 백업 유지. 배포 직전 수동 백업은 정기 보관 정리 대상에서 제외한다.

## 4. CI와 릴리스

### 4.1 트리거와 작업

`ci.yml`: `pull_request` 대상 dev/main, `push` dev/main. root-owned workflow가 backend/frontend/deploy 검증 job을 병렬 실행하고 마지막 `ci-gate`가 필수 job 전부 success인지 판정한다. 필수 검사에는 path filter를 걸지 않아 skipped 검사가 통과로 오인되지 않게 한다. PR의 오래된 실행만 취소할 수 있고 운영 배포는 중간 취소하지 않는다.

| Job | 명령·검증 | 성공 조건 |
|---|---|---|
| backend | `./gradlew --no-daemon test bootJar verifyBootJarNoLocalSecrets` | isolated Testcontainers MySQL, 실패/오류0, 실행 JAR에 local 비밀 설정 없음 |
| frontend | `npm ci`, `npm test`, `npm run lint`, `npm run build`(frontend 작업 디렉터리) | 모든 tests 통과, lint/typecheck/build exit0, production same-origin/S3 설정 |
| deploy-tools | `python3 -m unittest discover -s deploy -p 'test_*.py'`, shell syntax 및 CI 계약 검사 | 패키지·백업·새 pull 도구의 격리 테스트 통과 |
| ci-gate | `if: always()`로 needs 결과 검사 | 성공 job 누락·실패·취소·예상 밖 skip이면 실패 |

main push 실행에서만 ci-gate 후 package job을 실행한다. 같은 실행의 backend/FE 출력에 commit SHA/run ID/run attempt를 결속하며 다른 run의 출력을 섞지 않는다. 기존 package/verify를 실행해 성공한 tar.gz를 Actions artifact로 업로드한다. PR·dev에서는 운영 후보 package를 게시하지 않는다. 승인 후 재빌드하지 않는다.

### 4.2 패키지 출처

새 `manifest format=2`에 `sourceRevision`, `sourceDirty=false`, build run/attempt, JAR/FE 파일 SHA, Flyway SQL·Java migration/helper 목록·SHA를 기록한다. 기존 format1은 수동 검증/기존 release 유지용으로 읽을 수 있지만 신규 자동 배포 후보는 format2만 받는다. manifest에 출처를 적는 것만으로 신뢰하지 않고 GitHub API의 repo/run/workflow/SHA/artifact 정보와 대조한다.

artifact 이름: `zeroverse-<40자리 commit SHA>-<run ID>-<attempt>`. GitHub artifact ZIP의 digest와 내부 release tar.gz SHA는 서로 다른 필드로 검증한다. 저장·전송 한도는 각각 512MiB이며 압축을 푼 전체 데이터도512MiB, 파일 수10,000개 이하로 제한한다. 경로 이탈·절대 경로·중복 멤버·symlink/hardlink·특수 파일을 거부한다.

Actions artifact 보관 제안은30일이다. 배포된 release와 직전 정상 release는 서버에 보존한다. 첫 버전은 release 자동 삭제를 넣지 않고, 최근 정상3개를 유지하는 수동 정리 절차를 둔다. artifact가 만료됐으면 현재 main에서 새 검증 실행을 만들고 새로 승인한다. `latest`로 대체하지 않는다.

## 5. 승인 요청과 신뢰 경계

### 5.1 GitHub 운영자 설정

- 공개 저장소의 `production` Environment: required reviewer는 소유자 `0-virus`; 1인 운영을 위해 prevent self-review는 끈다. 관리자 우회는 끄고 deployment branch는 main만 허용한다.
- `main`/`dev`: PR 및 `ci-gate` 필수, force push/delete 금지. 1인 운영에서 자기 PR을 승인할 수 없는 required PR approvals 규칙은 무작정 켜지 않는다. CODEOWNERS는 경로 검토 안내이지 혼자 운영할 때 독립 인간 승인 증거가 아니다.
- workflow/배포 도구 변경은 독립 agent QA와 변경 근거를 기록한다. Actions는 검토한 full commit SHA로 고정하고 기본 `GITHUB_TOKEN` 권한은 `contents: read`다. PR 코드에 write token을 주는 `pull_request_target` checkout 방식은 쓰지 않는다.

### 5.2 단일 요청 식별자

`request-deploy.yml`은 **main에서의 `workflow_dispatch`만** 받는다. 입력은 `build_run_id`, `build_run_attempt`, `artifact_id`, `expected_current_release`다. URL·셸 명령·서버 경로를 입력받지 않는다. 최초 버전은 request workflow의 재실행(attempt>1)을 거부하고 새 dispatch를 요구해 승인 재사용을 피한다.

읽기 권한의 준비 job이 exact main push CI 완료·성공과 package를 대조해 요약을 보여준다. 승인된 `production` job에서 동일 조건을 다시 검사한다. `environment: {name: production, deployment: false}`를 사용해 승인 job의 완료가 운영 배포 성공으로 자동 표시되는 것을 피한다. 이 옵션과 required reviewers 조합은 실제 격리 인수에서 확인한다.

승인 job만 `deployments: write`를 갖는다. custom Deployment는 task=`zeroverse:deploy`, environment=`production`, ref=exact SHA, auto_merge=false, production_environment=true로 만든다. `required_contexts`의 commit-status 자동 검사에 CI 검증을 맡기지 않는다. 필요한 run/job 성공을 명시 검사한 뒤 이 필드는 빈 배열로 설정하며, 이것을 독립 CI 검증 생략으로 사용하지 않는다.

payload 계약(version1):

| 필드 | 규칙 |
|---|---|
| repository_id | `1253062454` 고정 |
| source_sha / release_id | 검증한40자리 SHA / ASCII 안전한 release ID |
| build_run_id / build_run_attempt / artifact_id | 양의 정수, GitHub API와 일치 |
| artifact_sha256 / package_sha256 | 외부 ZIP/내부 tar의64자리 SHA256 |
| request_run_id / request_run_attempt | 승인 workflow 실행, attempt는1 |
| expected_current_release | 승인 당시 운영 release ID. 서버 current와 다르면 거부 |
| expires_at | 요청 생성 후24시간, UTC |
| migration_files_sha256 | 후보의 migration 파일 목록·각 해시를 canonical 정렬해 해시한 값 |

Deployment 생성 후 같은 승인 job이 `approved-request-<run ID>-1` artifact를 게시한다. 내용은 `deployment_id`와 payload 전체다. 서버는 Deployment payload만 믿지 않고 이 **성공한 승인 workflow의 immutable 요청 artifact**와 byte/canonical JSON 일치를 확인한다. 토큰 탈취자가 별도 Deployment를 만들거나 다른 후보를 가리켜도 deployment ID/요청 증거가 일치하지 않으면 적용할 수 없다. 게시 중 실패한 workflow의 요청은 실행하지 않는다.

서버의 root-owned allowlist에 repo ID, CI/request workflow ID, 승인된 request workflow 및 호출 helper의 blob SHA, production environment ID, 승인자 numeric ID를 등록한다. worker는 API로 run/event/main/SHA/attempt/jobs 결론과 approval history의 production 승인·승인자 ID를 확인한다. 승인 이력 API에 없는 승인 시각 필드를 있다고 가정하지 않는다. attempt1 강제와 trusted workflow 코드·성공한 승인 job·요청 artifact를 함께 확인한다. workflow/helper 코드 변경 시 allowlist를 수동 검토·갱신하기 전 새 요청은 거부한다.

### 5.3 서버 GitHub 인증

전용 GitHub App을 이 저장소 하나에 설치한다. 권한은 Metadata read, Actions read, Contents read, Deployments write만 요청한다. App private key는 서버 `/etc/zeroverse-deploy/` root600, 앱 프로세스 접근 불가다. API installation token은1시간 만료이며 다운로드용 read token과 상태 보고용 deployments-write token을 작업별로 축소 발급한다. App에는 Actions/Contents/Administration write, 운영 Environment 승인 권한을 주지 않는다. 상태 보고 토큰은 요청 artifact를 만들 수 없다.

Python 표준 라이브러리와 OpenSSL subprocess로 JWT 서명/HTTPS를 구현하는 제안이며, 토큰은 메모리에만 유지한다. 키·Authorization·쿠키·artifact 다운로드 signed URL은 로그에 남기지 않는다.

네트워크 poller는 별도 비특권 사용자 `zeroverse-deploy`로 실행한다. root-owned broker만 App private key를 읽고, Unix socket의 peer UID를 확인해 이 저장소의 Actions/Contents/Deployments read token만 poller에 전달한다. root executor는 허용된 deployment ID만 입력받고 GitHub 출처를 다시 검증한다. 파일은 root private staging으로 복사한 후 그 복사본의 해시·형식을 검증하므로 poller가 검증 후 바꿀 수 없다. shell command·임의 경로·환경변수는 IPC 입력으로 받지 않는다.

상태 보고는 root journal의 허용된 ID/상태에서만 생성하며 broker가 축소된 Deployments write token으로 수행한다. poller에는 상태 쓰기 token과 App key를 주지 않는다. App 하나의 최대 권한은 같지만 프로세스·발급 token·파일 소유권을 분리한다. root 자체가 침해되면 호스트를 보호할 수 있다는 주장은 하지 않는다. helper 코드·설정은 root 소유, key0600, private staging0700, systemd hardening을 적용한다. poller용 비밀 없는 allowlist 사본만 root 소유0644로 읽게 하고 root journal/키 디렉터리에는 접근시키지 않는다. poller의 요청 제출과 상태 조회는 고정 broker IPC로 처리한다.

## 6. 서버 pull·적용·복구

### 6.1 기본 동작

- `zeroverse-deploy.timer`:60초 주기, 중복 시작 금지. 서비스는 `--once`로 실행되고 활성화 기본값은 false다. 입력은 로컬 고정 config와 GitHub의 검증된 요청뿐이다.
- 전용 `/var/lib/zeroverse-deploy/cicd/`에 durable journal/receipts, `/var/lib/zeroverse-deploy/cicd/staging/`에 root private staging, 별도 `/var/cache/zeroverse-deploy/`에 비특권 다운로드 공간을 둔다. 기존 수동 배포 파일을 덮어쓰지 않는다.
- API timeout20초, 요청 전체 준비 timeout120초. GitHub 오류·권한/키 만료·후보 누락이면 현재 앱을 건드리지 않고 실패/대기 상태를 남긴다.
- `.maintenance.lock` 하나를 배포·정기/수동 백업 진입점이 공유한다. 락이 사용 중이면 이번 poll은 종료한다. lock 소유자가 하위 backup 프로세스를 호출할 때 재획득하여 deadlock하지 않도록 wrapper와 unlocked 내부 실행을 분리한다. 기존 backup script를 직접 실행하면 공용 lock을 우회한다는 점을 가이드에 명시하고, 운영 진입점은 wrapper로 통일한다.
- host flock와 journal의 deployment ID/최종 상태가 중복 실행을 막는다. 재전달된 terminal 요청은 변경 없이 보고만 재시도한다. 여러 미처리 요청/expected-current 충돌은 자동 큐 소비하지 않고 운영자가 취소·새 승인하도록 한다. bootstrap 이전 요청과24시간이 지난 요청은 실행하지 않는다.

### 6.2 적용 순서

1. 승인 출처·artifact digest·tar manifest·현재 release·디스크 여유를 확인하고 root-owned 새 release 디렉터리에만 설치한다. 기존 release 덮어쓰기 금지. GitHub에서 내려받은 설치 스크립트는 실행하지 않는다.
2. 후보/현재 JAR의 Flyway migration 파일·SHA 및 운영 Flyway history의 version/type/script/checksum/success를 읽기 전용 대조한다. `BOOT-INF/classes/db/migration/**`의 SQL과 Java class(내부 class 포함), V5가 사용하는 `PostTextExtractorV1` class 집합을 fingerprint에 넣는다. 알려지지 않은 migration 종류·helper 의존 변경은 수동 검토한다. 파일 집합/바이트가 달라지면 기존 앱을 유지하고 `MANUAL_MIGRATION_REQUIRED`로 종료한다. 초기 활성화 때 baseline 파일 SHA ↔ 실제 DB history 매핑을 검증·보관한다. SHA256과 Flyway checksum은 다르며 Java migration의 nullable checksum을 SQL checksum처럼 취급하지 않는다.

   현재 `application-prod.yml`은 Flyway enabled=true다. 자동 경로 도입 시 root-owned systemd drop-in의 ExecStart에 `--spring.flyway.enabled=false --spring.jpa.hibernate.ddl-auto=validate`를 고정하여 후보·복구 앱 모두 startup migration을 실행하지 않게 한다. 이는 제안이며 현 서비스는 변경하지 않았다. DB history 사전검사와 Hibernate validate를 별도로 수행하고, 이것을 Flyway validate 실행과 같다고 부르지 않는다. baseline은 기존 수동 배포 검증 결과/실제 history와 대조하며 기준 불명·누락 row이면 활성화를 거부한다. migration이 필요한 릴리스는 timer 중단·별도 백업/검증·수동 마이그레이션 승인 절차 후 baseline을 다시 확정한다. false 설정으로 새 빈 DB를 초기화하려 하지 않는다.
3. `APPLYING`을 fsync+atomic journal에 기록하고 GitHub 상태를 in_progress로 보고한다. Caddy를503/no-store 점검 화면으로 전환하고 기존 앱을 정상 종료한다(기존 systemd stop 한도45초). 강제 종료·종료 실패는 후보 실행 없이 복구 대상으로 처리한다. 앱이 멈춘 뒤 암호화 수동 백업을 만들므로 진행 중 DB 쓰기가 종료된 시점을 확보한다. 이미 발급된 S3 PUT은 DB 변경과 별개이며 이번 배포에서 S3 객체를 정리하지 않는다.
4. 백업 SHA/파일 소유자·0600·nonempty를 검증한다(최대300초). 실패하면 current를 바꾸지 않고 이전 앱 재기동/readiness 확인 후 공개 화면을 복원한다. 신규 다운로드 파일만 남기고 사용자 자료는 보존한다.
5. `current.next`가 없는지 확인하고 atomic symlink 교체 → 후보 앱 기동 → readiness 최대120초. 적용 전후 DB history가 같아야 한다.
6. 공개 트래픽 재개 전에 별도 loopback Caddy 검증 경로로 후보 index 및 참조 asset을 정확한 hash와 대조한다. 정상일 때 공개 Caddy 설정을 복구한 뒤 외부 HTTPS root/signin·asset·읽기 전용 public API를 확인한다. 공개 readiness/Swagger 차단은 유지한다. 새 제품 health/version API는 만들지 않는다.
7. 성공 시 current/previous-good/commit/artifact/deployment ID를 durable 기록하고 GitHub Deployment를 success로 보고한다. Actions 요청 workflow의 녹색 표시는 요청 제출 완료일 뿐이며 이 Deployment success가 실제 배포 완료다.

### 6.3 실패·재시작 상태

상태: `DISCOVERED → VERIFIED → APPLYING → SUCCEEDED`; 오류는 `REJECTED`, `FAILED_RECOVERED`, `MANUAL_INTERVENTION`, 결과 전송만 실패하면 `REPORT_PENDING`이다.

- current 전환 후 실패: candidate 종료 → DB history가 적용 전과 같고 검증된 previous-good가 있을 때만 포인터 복귀 → 이전 앱 readiness → 공개 복원. 원래 요청은 실패이고 복구 성공은 별도 필드다.
- DB history 변경/불명, 이전 앱 미기동, 설치/전환 중 crash로 실제 상태를 특정할 수 없음:503 유지·timer 일시 중단·manual intervention. DB 자동 복원/다운그레이드 금지. 상태를 보지 않고 재시도하지 않는다.
- 정상 서비스인데 GitHub 상태 보고만 실패: `REPORT_PENDING` 재전송. 앱 재배포·재시작·재백업 금지.
- 운영자가 timer를 멈춰도 진행 중 oneshot이 자동 취소되지는 않는다. 상태를 확인한 후 절차적으로 종료/복구한다. emergency로 kill한 상태는 자동 재개하지 않는다.
- CI dispatch concurrency는 한 번에 한 요청 생성만 제한한다. 실제 배포 상호 배제·순서·중복 보장은 서버 lock/journal이 담당한다.

## 11. 근거와 문서 유지

- [GitHub hosted runner IP](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#ip-addresses): 일반 runner 대역을 SSH 허용목록으로 넓히지 않는 선택 근거.

- [Artifacts API](https://docs.github.com/en/rest/actions/artifacts): artifact ID/digest/workflow_run 및 Actions read 권한.
- [Deployment API](https://docs.github.com/en/rest/deployments/deployments): exact ref, task, auto_merge/required_contexts 명시.
- [승인 이력 API](https://docs.github.com/en/rest/actions/workflow-runs#get-the-review-history-for-a-workflow-run): 승인자·환경 교차 확인.
- [GitHub App installation 인증](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation): repository/permission 제한,1시간 token.
- [Actions 보안 지침](https://docs.github.com/en/actions/reference/security/secure-use): action SHA 고정·untrusted code/권한 분리.
